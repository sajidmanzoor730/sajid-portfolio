BI Validation & Monitoring

Practical controls used to check whether an operational reporting layer is producing trustworthy KPIs. This page documents the portfolio implementation without claiming production monitoring infrastructure.

← Back to Helpdesk case studyView Power BI model →

Source-to-report reconciliation

✓Ticket volumeCompare unique Ticket_ID counts between ETL, SQL and BI.
✓SLA adherenceReconcile the percentage against the SQL analytical baseline.
✓Resolution & CSATCheck average resolution hours and CSAT against the curated dataset.
✓Repeat & escalationValidate both rates before publishing KPI views.

Data-quality gates

  • Ticket_ID must be unique after ETL.
  • Created_At must be populated.
  • Priority must be P1–P4.
  • Channel and status values must match the defined source lists.
  • Resolved_At cannot precede Created_At.
  • SLA_Breach must be Yes/No.
  • CSAT must be between 1 and 5 when present.
  • The curated dataset must contain records.

Refresh review

A practical refresh review records:

  • raw row count
  • curated row count
  • duplicates removed
  • rejected records
  • data-quality status
  • KPI reconciliation status

The Streamlit dashboard exposes the ETL audit values so they can be inspected alongside the operational report.

Investigation workflow

  1. Check source and curated row counts.
  2. Review duplicate and rejected-record counts.
  3. Compare the changed KPI with the SQL baseline.
  4. Break the metric down by date, priority, team and category.
  5. Inspect the underlying exception records.
  6. Document the cause before changing reporting logic.
Realistic scope: The project demonstrates these controls and the analytical workflow. It does not claim a live Power BI gateway, scheduled enterprise refresh, production warehouse, OLAP platform or alerting system.
