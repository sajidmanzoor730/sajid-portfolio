VoIP Incident Troubleshooting Toolkit

A practical support-engineering workflow for turning SIP/RTP packet evidence and service logs into structured investigation notes, testable hypotheses and clear escalation steps.

View GitHub repository → Back to all projects

What this project demonstrates

The workflow starts with packet or log evidence, extracts relevant SIP, SDP and RTP details, organizes the findings, and documents what is confirmed versus what still needs checking. The aim is to make troubleshooting repeatable rather than jump to a root-cause conclusion from a symptom alone.

SIP registration analysis

Python parsing of sanitized SIP log fixtures, including the distinction between a 401 digest-authentication challenge and a confirmed registration rejection such as 403.

RTP and one-way audio

Wireshark/TShark filters and packet-level review to examine RTP direction, stream presence, payload details and timing before forming a media-path hypothesis.

Structured evidence with SQL

SQLite schema and investigation queries organize extracted evidence so related events and measurements can be reviewed consistently.

API health checks

A Postman collection exercises public HTTP test endpoints and provides a repeatable starting point for checking request/response behavior.

Investigation workflow

  1. Capture the reported symptom and identify the affected call or registration attempt.
  2. Inspect SIP signaling and relevant SDP details; note response codes and transaction sequence.
  3. For media symptoms, inspect RTP in both directions and review stream measurements rather than assuming a network cause.
  4. Parse available log fixtures with Python and load structured evidence into SQLite for targeted queries.
  5. Separate observed facts from hypotheses, list missing evidence and document the next diagnostic or escalation step.

Worked investigation scenarios

SIP 403 registration rejection

Walkthrough of a registration attempt rejected with 403, focusing on the signaling evidence and the checks needed before assigning a cause.

One-way audio after answer

Walkthrough of RTP direction and packet evidence to determine whether media is visible in both directions and what additional network or endpoint evidence is needed.

401 challenge followed by success

Shows why a SIP 401 response can be part of a normal digest-authentication exchange and should not automatically be labelled a registration failure.

API and SMS troubleshooting

Additional guidance covers HTTP/API triage, safe retry considerations, message lifecycle interpretation and delivery callback checks.

Tools and repository contents

Python for SIP log parsing and validation · Wireshark/TShark for packet inspection · SQLite/SQL for evidence queries · Postman for API health checks.

  • sip-parser/ — parser and sanitized sample log fixture
  • wireshark/ — display filters for SIP, RTP, DNS and TCP
  • sql/ and python-sql/ — evidence schema and analysis queries
  • docs/ — runbook, worked incidents and API/SMS troubleshooting guide
  • tests/ — parser and fixture validation tests
Evidence and scope: This is a learning and portfolio project, not production support experience. The packet evidence comes from public Wireshark sample captures and documented examples. No customer, employer or live telecom data is used. Each worked scenario distinguishes what the sample evidence proves from hypotheses that would require further investigation.
