01 · What is inside

Built around real support-engineering tasks

The toolkit focuses on the work behind a good technical investigation: reproduce the symptom, inspect the right layer, collect evidence, and explain what is known without overstating the root cause.

01 / SIGNALING

SIP registration analysis

Parse sanitized REGISTER exchanges and distinguish authentication challenges from authorization rejections. Identify the next identity, account or policy checks.

Python · SIP response codes

RTP & one-way audio

Use packet filters and stream inspection to check whether media is present in both directions. Compare SDP negotiation with observed packet endpoints.

Wireshark · TShark · RTP

02 · Visual workflow

From symptom to evidence-based next step

A repeatable sequence helps avoid guessing at a network, endpoint or provider cause before the relevant evidence has been checked.

Investigation sequence

  1. Define the symptom
    Capture time, timezone, affected endpoint, call or request identifier, and exact behavior.
  2. Inspect signaling
    Review SIP transaction order, response codes and SDP offer/answer details.
  3. Check media evidence
    Inspect RTP streams in both directions; compare packet endpoints with negotiated SDP addresses and ports.
  4. Structure and query
    Parse available logs and use SQL to correlate the evidence consistently.
  5. Document and escalate
    Separate confirmed observations from hypotheses and list the next evidence required.

03 · Worked examples

Three scenarios, with evidence limits made clear

These walkthroughs use synthetic log fixtures. They demonstrate diagnostic reasoning, not customer incidents or proven production root causes.

CASE 01 · REGISTRATION

SIP 403 rejection

Observed in fixture: two 403 responses after REGISTER attempts. A 403 indicates refusal; repeating the same request is unlikely to fix an authorization or policy rejection.

Next checks: account identity, endpoint assignment, source-IP/domain policy and registrar-side authorization logs.

Finding: authorization investigation
CASE 02 · MEDIA

One-way audio after answer

Observed in fixture: INVITE, 180, 200, a reported one-way-audio symptom and BYE. The fixture does not contain SDP bodies or bidirectional RTP packet evidence.

Next checks: compare SDP, inspect RTP both ways, then review NAT/firewall and media-relay evidence.

Finding: media-path investigation only
CASE 03 · AUTHENTICATION

401 challenge, then accepted

Observed in fixture: a 401 challenge followed by an authenticated REGISTER accepted event. A single 401 is not automatically a registration failure.

Next checks: if retry fails, verify nonce/realm handling and the digest response without exposing credentials.

Finding: successful challenge flow

05 · API troubleshooting

Separate request acceptance from final delivery

The repository also includes a Twilio-style API/SMS practice guide. It uses placeholders and simulated examples; it is not a record of customer tickets.

HTTP triage guide

400Check required fields, formatting and validation details.
401Check authentication method; never request secrets in a ticket.
403Check account state, permissions and sender eligibility.
429Review rate limits; use bounded backoff with jitter.
5xx / timeoutCheck provider status and request IDs before retrying.
