02 · Method

A repeatable investigation process

Each step answers a different question. This prevents assumptions about NAT, firewall, endpoint or provider behavior from being presented as confirmed findings.

Five-step investigation

  1. Scope the symptom
    Record exact time and timezone, affected endpoint, call/request ID and reproduction steps.
  2. Read the signaling
    Follow SIP transaction order, response codes, headers and SDP offer/answer details.
  3. Verify media flow
    Inspect RTP in both directions and compare packet endpoints with negotiated SDP addresses and ports.
  4. Correlate observations
    Parse logs and query related events using Python and SQL.
  5. Write the handoff
    Separate confirmed facts, hypotheses and the next diagnostic evidence required.

03 · Diagnostic examples

How the investigation logic is applied

These are synthetic walkthrough fixtures used to demonstrate reasoning. They are not customer incidents or verified production root causes.

CASE 01 · REGISTRATION

SIP 403 rejection

Observed: repeated 403 responses after REGISTER attempts. A 403 indicates refusal; repeating the same request is unlikely to resolve an authorization or policy rejection.

Next: verify account identity, endpoint assignment, source-IP/domain policy and registrar-side logs.

Authorization checks
CASE 02 · MEDIA

Reported one-way audio

Observed: call setup and teardown events plus a reported symptom. The fixture does not include SDP bodies or bidirectional RTP packet evidence.

Next: compare SDP, inspect RTP both ways, then review NAT/firewall and media-relay evidence.

Media-path investigation
CASE 03 · AUTHENTICATION

401 challenge then accepted

Observed: a 401 challenge followed by an accepted authenticated REGISTER. A single 401 is not automatically a registration failure.

Next: if retry fails, check nonce/realm handling and digest response without exposing credentials.

Digest authentication
