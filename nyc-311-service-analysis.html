NYC 311: Where Service Is Fast, Slow and Repeated

An end-to-end analysis of 343,133 real New York City 311 service requests from July 2026: data-quality checks, cleaning, SQL analysis, findings and a recommended action for each.

Data note: This project is designed around real public data, not generated data. Source: NYC Open Data, "311 Service Requests from 2020 to Present", for requests created 1 to 31 July 2026. Request status is as of the extract. It covers one month and has no population adjustment, so borough counts are volumes, not rates. For reproducibility, run the official-data workflow in GitHub Actions; it downloads a fresh extract, runs quality checks and executes every SQL query.

1. What people complain about

Demand is concentrated: three complaint types make up 30.4% of all requests, and the top 15 make up 61.6%. It also differs by borough. Illegal Parking is the top complaint in Brooklyn and Queens, street noise leads in the Bronx and Manhattan, and damaged trees lead on Staten Island. 460 requests have no usable borough and are left out of the borough view.

Decision this supports: Set response capacity by borough and complaint type instead of one citywide allocation. Parking and noise first, with tree crews weighted toward Staten Island.

2. How fast each agency closes requests

Closing speed varies enormously. NYPD closes 99.4% of its requests within 24 hours (median 1.3 hours). HPD closes only 4.1% within 24 hours and 37.4% within 7 days, with a median of 261 hours (about 11 days), on 54,788 requests, which is 16% of all volume. DOHMH is slower still: 1.8% in 24 hours and 36.0% in 7 days.

Read with care: Time to close is created to closed as recorded. An agency can close a request administratively, so fast is not automatically good. Medians use closed requests only, so agencies with many still-open requests look faster than they really are.
Decision this supports: Ask HPD and DOHMH whether their closing times are real service levels or how their process closes tickets, then publish a target per complaint type instead of per agency. HPD alone is large enough to move the city-wide picture.

3. Requests still open months later

DPR has 4,140 requests from the first half of July still open at download, which is 20.6% of everything it received. TLC closes only 23.6% of its requests at all, and 1,081 of its 2,963 requests from the first half of the month are still open. These requests were at least 11 weeks old when the data was downloaded.

Open requests created in the first half of July

Decision this supports: Audit DPR and TLC open items first and decide whether they are unresolved work or tickets never closed in the system. They are the two agencies where open requests are a large share of what they received.

4. Repeat complaints about the same place

38.8% of requests that carry an address sit at an address and complaint type with three or more requests that month. The extreme cases are striking: one address logged 1,099 "Noise - Residential" requests in a month. Even so, the 15 biggest address-and-type combinations total only 5,972 requests, so repeating is widespread rather than limited to a few addresses. Large apartment buildings will naturally generate several requests.

5. When requests arrive

Requests peak between 9 am and noon (20,289 at 10:00) and have a second, smaller peak at 9 and 10 pm (18,708 and 18,823 an hour). The quietest hour is 4:00 with 3,485. Daily volume fell through the month: the last 7 days averaged 10,604 requests a day against 12,476 in the first 7 days (-15%).

6. How people contact 311

Online and mobile bring 68.4% of requests; phone is still 22.2%, and 9.0% have an unknown channel.

Requests by channel

Decision this supports: Focus on the 22% who still phone when looking at cost per request, and fix the channel field so the 9% unknown can be classified.

7. Data quality and method

The data was in good shape: no duplicate keys, no malformed zip codes and no coordinates outside the city. The one real defect was 74 requests whose closing date is earlier than their creation date. Their closing dates were blanked so they cannot distort response times.

Things to know before trusting the numbers

  • One month only. July is not a full year, so seasonality is not covered.
  • Complaint names are not standardised. Some types are written in capitals (UNSANITARY CONDITION, PLUMBING, PAINT/PLASTER) while others are in title case. They were left as published; grouping is unaffected, but a production report would map them to one format.
  • Unspecified boroughs. 460 requests have no usable borough.
  • Still to check: hour 0 has 12,610 requests against 8,748 at hour 1. That may be real late-night demand or requests stamped exactly 00:00:00. The query midnight_check in the SQL file tests this; I have not run it yet.
  • Closing speed is not quality. See the note in section 2.

8. The SQL

This is the full SQL file (SQLite). The page includes the complete SQL analysis. The last two queries, weekday_avg_per_day and midnight_check, were added after the initial result snapshot; use the official-data workflow to execute them against a fresh real-data extract before relying on those outputs.

nyc311/queries.sql All queries
-- SQL analysis of the cleaned 311 extract. Table: r  (one row per service request). SQLite dialect.
-- Run with: python3 run_analysis.py

-- name: top_complaint_types
SELECT complaint_type,
       COUNT(*) AS requests,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM r), 1) AS share_pct
FROM r
GROUP BY complaint_type
ORDER BY requests DESC
LIMIT 15;

-- name: borough_volume
SELECT borough,
       COUNT(*) AS requests,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM r WHERE borough <> 'Unspecified'), 1) AS share_pct
FROM r
WHERE borough <> 'Unspecified'
GROUP BY borough
ORDER BY requests DESC;

-- name: requests_by_hour
SELECT created_hour AS hour, COUNT(*) AS requests
FROM r
GROUP BY created_hour
ORDER BY created_hour;

-- name: weekday_pattern
SELECT weekday, COUNT(*) AS requests
FROM r
GROUP BY weekday
ORDER BY requests DESC;

-- name: channel_mix
SELECT open_data_channel_type AS channel,
       COUNT(*) AS requests,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM r), 1) AS share_pct
FROM r
GROUP BY open_data_channel_type
ORDER BY requests DESC;

-- name: agency_performance
-- Closure rate, share of closed requests finished within 24 hours / 7 days, average hours to close
SELECT agency,
       COUNT(*)                                                    AS requests,
       ROUND(100.0 * SUM(is_closed) / COUNT(*), 1)                 AS closed_pct,
       ROUND(100.0 * SUM(closed_within_24h = 1)
             / NULLIF(SUM(closed_within_24h IS NOT NULL), 0), 1)   AS closed_within_24h_pct,
       ROUND(100.0 * SUM(closed_within_7d = 1)
             / NULLIF(SUM(closed_within_7d IS NOT NULL), 0), 1)    AS closed_within_7d_pct,
       ROUND(AVG(response_hours), 1)                               AS avg_response_hours
FROM r
GROUP BY agency
HAVING COUNT(*) >= 500
ORDER BY requests DESC;

-- name: backlog_by_agency
-- Requests still open at download time that were created more than 14 days before the extract's last day
-- (roughly the first half of the month). Their real age at download is much larger than 14 days.
SELECT agency,
       COUNT(*) AS open_over_14_days
FROM r
WHERE is_closed = 0
  AND julianday((SELECT MAX(created_date) FROM r)) - julianday(created_date) > 14
GROUP BY agency
ORDER BY open_over_14_days DESC
LIMIT 10;

-- name: top3_complaints_per_borough
-- RANK within each borough
WITH c AS (
  SELECT borough, complaint_type, COUNT(*) AS requests
  FROM r
  WHERE borough <> 'Unspecified'
  GROUP BY borough, complaint_type
), ranked AS (
  SELECT *, RANK() OVER (PARTITION BY borough ORDER BY requests DESC) AS rnk
  FROM c
)
SELECT borough, rnk AS rank, complaint_type, requests
FROM ranked
WHERE rnk <= 3
ORDER BY borough, rnk;

-- name: daily_volume_trend
-- Day-over-day change (LAG) and 7-day moving average (window frame)
WITH d AS (
  SELECT substr(created_date, 1, 10) AS day, COUNT(*) AS requests
  FROM r
  GROUP BY day
)
SELECT day,
       requests,
       requests - LAG(requests) OVER (ORDER BY day)                              AS change_vs_prev_day,
       ROUND(AVG(requests) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 0) AS moving_avg_7d
FROM d
ORDER BY day;

-- name: repeat_locations
-- Same address, same complaint type, five or more requests in the extract
SELECT incident_address, complaint_type, COUNT(*) AS requests
FROM r
WHERE incident_address IS NOT NULL
GROUP BY incident_address, complaint_type
HAVING COUNT(*) >= 5
ORDER BY requests DESC
LIMIT 15;

-- name: repeat_location_share
-- How much of the volume is repeat complaints about the same address and type?
WITH g AS (
  SELECT incident_address, complaint_type, COUNT(*) AS n
  FROM r
  WHERE incident_address IS NOT NULL
  GROUP BY incident_address, complaint_type
)
SELECT SUM(n)                                                        AS requests_with_address,
       SUM(CASE WHEN n >= 3 THEN n ELSE 0 END)                       AS requests_at_repeat_locations,
       ROUND(100.0 * SUM(CASE WHEN n >= 3 THEN n ELSE 0 END) / SUM(n), 1) AS repeat_share_pct
FROM g;

-- name: weekday_avg_per_day
-- Weekday totals mislead when a month has 5 of some weekdays and 4 of others; average per calendar day instead
WITH d AS (
  SELECT substr(created_date, 1, 10) AS day, weekday, COUNT(*) AS n
  FROM r
  GROUP BY day, weekday
)
SELECT weekday,
       COUNT(*)                         AS days_in_extract,
       SUM(n)                           AS requests,
       ROUND(1.0 * SUM(n) / COUNT(*), 0) AS avg_requests_per_day
FROM d
GROUP BY weekday
ORDER BY avg_requests_per_day DESC;

-- name: midnight_check
-- Hour 0 is much busier than hour 1. Are many requests stamped exactly 00:00:00 (a placeholder time)?
SELECT SUM(created_hour = 0)                              AS hour_0_requests,
       SUM(substr(created_date, 12, 8) = '00:00:00')      AS stamped_exactly_midnight
FROM r;

9. Reproduce it

The whole pipeline is in the nyc311 folder of the project. With Python 3.9+ and pandas installed:

python3 download_311.py --start 2026-07-01 --end 2026-08-01
python3 quality_checks.py
python3 clean_311.py
python3 run_analysis.py
python3 build_page.py   # rebuilds this page from the results
