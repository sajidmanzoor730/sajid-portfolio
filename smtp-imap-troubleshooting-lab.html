01 / What it does

Diagnose the layer, not just the symptom.

Three capabilities that turn a raw socket error or server reply into a next step.

SMTP

Outbound mail checks

Walk through TCP connection, server banner, EHLO, STARTTLS or implicit TLS, authentication and recipient-envelope checks.

IMAP

Mailbox connectivity

Probe IMAP over SSL or STARTTLS, inspect server responses and test password or XOAUTH2 authentication.

Diagnosis

Actionable failure mapping

Classify reply codes and socket/TLS errors into network, TLS, authentication, policy or transient categories with recommended next steps.

02 / Diagnostic workflow

From connection attempt to evidence-based next step.

Five stages, in order, so the failing layer is identified before anyone guesses at a fix.

  1. 01 · CONNECTDNS + TCPCheck name resolution, reachability, timeouts and refused connections.
  2. 02 · NEGOTIATESMTP / IMAP + TLSInspect protocol banners, capabilities, STARTTLS and certificate validation.
  3. 03 · AUTHENTICATELOGIN / XOAUTH2Exercise authentication safely; mask credentials and bearer tokens in transcripts.
  4. 04 · CLASSIFYFailure categoryMap server replies and transport errors to likely causes and practical checks.
  5. 05 · REPORTNext actionProduce readable or JSON output that can support repeatable troubleshooting.
03 / Safe reproduction

Reproduce failures without depending on a live mail provider.

Local mock servers and conservative defaults keep diagnostics repeatable and safe.

Fault-injecting mock servers

Local SMTP and IMAP mocks reproduce unavailable STARTTLS, reset connections, authentication failures, relay denial, greylisting, banner errors and blackholed connections.

Read-only verification

Probes do not send a message body. The SMTP envelope check stops after RCPT TO and issues RSET, avoiding message delivery during diagnostics.

Credentials stay out of the logs

Passwords and OAuth2 tokens are read from environment variables, and authentication payloads are redacted in transcripts. Avoid placing secrets in command history or shared logs.

TLS verified by default

Certificate verification is enabled by default. Credentials are blocked on unencrypted connections unless an explicit override is used for local lab work.

05 / Authentication and test coverage

Modern authentication with repeatable local tests.

XOAUTH2 support, automated regression tests and a clear statement of what has and has not been verified.

OAuth2 refresh exchange

Exchanges an already-issued refresh token for a short-lived access token. Interactive consent, initial authorization-code handling and persistent token rotation are outside the toolkit's scope.

SMTP / IMAP XOAUTH2

Supports bearer-token authentication flows for SMTP and IMAP, with token redaction in diagnostic transcripts.

Automated tests and CI

The latest checked CI run passed the test suite on Python 3.11, 3.12 and 3.13, with 54 tests per version. Local regression tests cover protocol behavior, mock-server scenarios, CLI flows and OAuth2/XOAUTH2 paths.

Scope and provider validation. Provider-specific Gmail and Microsoft 365 smoke tests are opt-in, need authorized test-mailbox secrets and have not been claimed as completed. Local mock tests are not proof of live-provider compatibility.
06 / Run it locally

Quick start.

Clone it, install it, explain a reply, then probe a local mock server.

terminal
git clone https://github.com/sajidmanzoor730/smtp-imap-troubleshooting-lab.git
cd smtp-imap-troubleshooting-lab
python3 -m pip install -e .
  # Explain a server reply
maillab explain 454 "4.7.0 TLS not available"

# Run the local mock and probe it
maillab mock smtp --mode starttls_unavailable --port 2525
maillab smtp 127.0.0.1 --port 2525 --mode starttls
Output of the explain command above
maillab explain
$ maillab explain 454 "4.7.0 TLS not available"

TLS: TLS/STARTTLS could not be negotiated
Likely causes:
  - Server cannot start TLS (certificate, config or resource problem)
  - A firewall or SMTP inspection feature is interfering with STARTTLS
  - Client and server share no TLS version or cipher
Next steps:
  - Capture on port 587 and look for the STARTTLS reply and the TLS ClientHello after it
  - Test the same host from another network to separate a customer firewall from a server fault
  - Try implicit TLS on 465 as a workaround and confirm with the customer
  - Check the certificate chain and supported TLS versions with openssl s_client
Scope and safety. Use the probes only against mail servers and accounts you own or are authorized to test. Provider smoke testing requires separately configured, user-authorized credentials. The project uses local mock servers for its automated protocol-failure tests.

07 / Engineering design

From protocol checks to a support-ready investigation.

Design choices that keep the toolkit easy to test and useful in a real support workflow.

Modular diagnostic layers

Separate SMTP, IMAP, OAuth2 and CLI responsibilities keep protocol handling, credential acquisition and user-facing output easier to reason about and test.

Repeatable local reproduction

Fault-injecting mock servers let the engineer reproduce protocol failures without relying on a live provider, customer mailbox or external network condition.

Incident-oriented output

Diagnostic categories and next-step guidance are intended to help turn a raw socket or server response into a clear support investigation.
